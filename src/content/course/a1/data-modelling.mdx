## Why data comes first

Screens change every few months. Code gets rewritten. But data sticks around, and every migration of real data is slow and risky. That's why the data model is often the most load-bearing decision in a product. Time spent here is repaid many times over.

## The vocabulary

| Term | Plain meaning | In Pocket Ledger |
|---|---|---|
| **Entity** | A kind of thing you store | User, Expense, Category |
| **Table** | Where one entity's records live | `expenses` |
| **Primary key (PK)** | The unique id of each row | `expenses.id` |
| **Foreign key (FK)** | A column pointing at another table's row | `expenses.user_id` → `users.id` |
| **Relationship** | How entities connect | One user has many expenses |
| **Constraint** | A rule the database itself enforces | `amount_paise > 0`, unique email |
| **Index** | A lookup shortcut that makes some queries fast | `(user_id, spent_on)` for monthly totals |
| **Migration** | A versioned script that changes the schema | "add a `note` column" |

## Decisions that are painful to undo

These are worth deciding deliberately, because changing them later means migrating real data.

1. **How money is stored.** Never as floating-point numbers: `0.1 + 0.2` isn't exactly `0.3` in a float. Store the smallest unit as an integer (`amount_paise bigint`), or use an exact decimal type. Decide the currency story now, even if it's "rupees only".
2. **Ids.** Sequential numbers (`1, 2, 3`) are simple but reveal how many records exist and are easy to guess. Random UUIDs avoid both. Either is fine; switching later is painful.
3. **Deleting.** A **hard delete** removes the row. A **soft delete** sets `deleted_at` and hides it. Soft deletes allow undo and audits, but every query must remember to filter them out.
4. **Time.** Store timestamps in UTC with time zone (`timestamptz`). Store "the day something happened" as a plain `date`. Mixing these up causes off-by-one-day bugs at midnight.
5. **Who owns what.** Every user-owned row carries `user_id`, and every query filters by it. This is the foundation of your security, not just your data.

## Let the database enforce rules

Put rules in the database as constraints, not only in code. Code has bugs and many entry points; the database is the last line of defence. `CHECK (amount_paise > 0)`, `UNIQUE (user_id, name)` and `NOT NULL` cost nothing and catch mistakes that tests miss, including mistakes agents make.

<Breaks title="Floats for money">
  <BreakPart label="What happens">

  An agent stores amounts as `float`. Totals are off by a paisa here and there. Nobody notices until a user's monthly report is ₹0.01 off from their bank statement, and fixing it means migrating every stored amount.

  </BreakPart>
  <BreakPart label="The fix">

  Decide money storage in the data model before any code exists, write it as a product rule in AGENTS.md, and back it with a database type that makes floats impossible.

  </BreakPart>
</Breaks>
