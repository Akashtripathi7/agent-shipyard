<Analogy>
  <p>A safe-deposit box. The bank stores the box, guards the building, and moves it between vaults, but only you hold the key. Even if a thief breaks into the bank, or a bank employee goes rogue, your box stays shut. That's the difference between "the bank keeps it safe" and "nobody but me can open it".</p>
</Analogy>

## Three places to encrypt

| Where | Protects against | How |
|---|---|---|
| **In transit** | Someone intercepting network traffic | HTTPS everywhere. Non-negotiable, and usually handled by your host. |
| **At rest** | Someone stealing disks or backups | Disk and database encryption. Usually a setting on managed hosts. |
| **End to end** | Anyone on the server side, including you and a compromised server | Encrypt on the user's device; the server only ever stores ciphertext |

The first two are table stakes. The third is an architecture decision, and it changes everything downstream.

## Zero-knowledge design

In a **zero-knowledge** system, the server stores data it has no way to read. Project L2, Vault, works like this:

1. The user's **master password** never leaves the device.
2. On the device, a **key-derivation function** (Argon2id again, with strong parameters) turns the master password into an encryption key.
3. Each vault item is encrypted on the device with that key, using an authenticated encryption method such as **AES-GCM**, before it's sent anywhere.
4. The server stores only encrypted blobs. Even a full database leak reveals nothing readable.

The cost is real and must be decided deliberately: **if the user forgets their master password, nobody can recover their data**, including you. No "reset password" link can bring it back. Zero-knowledge products either accept that or offer a recovery key the user must keep safe. That's a load-bearing product decision, and it belongs in an ADR.

## Never roll your own crypto

Use a well-known, maintained library, and its high-level functions. The most dangerous code an agent can write is its own encryption scheme: it will look plausible, pass every test you think of, and be broken in ways only a cryptographer would spot. Your review skill should treat any hand-written cryptography as a blocker.

## Secrets

**Secrets** are values that grant access: database passwords, API keys, token-signing keys. Rules, in order of how often they're broken:

1. **Never in the repository.** Not even briefly; git history keeps them forever. Use environment variables locally (`.env`, gitignored) and the host's secret settings in production.
2. **Never in chat or logs.** Don't paste a real key into an agent session; don't log request bodies or headers that carry tokens.
3. **Scanned mechanically.** A tool like gitleaks blocks commits that contain secrets (Part 4 sets it up).
4. **Rotatable.** Know how to replace each secret quickly if it leaks, and practise it once.
5. **Least privilege.** A key that can only read one bucket leaks less than one that can do everything.

4. Keep both. They become the starting point for Project L2's architecture milestone.

</Exercise>

<Breaks title="The debug log that leaked the vault">
  <BreakPart label="What happens">

  While debugging sync, an agent adds a log line that prints the decrypted vault item "temporarily". It ships in a release. Every sync now writes plaintext passwords to the device logs, which crash reporters upload.

  </BreakPart>
  <BreakPart label="The fix">

  An AGENTS.md rule ("never log decrypted data, secrets or tokens, even temporarily"), a review-skill check for logging near crypto code, and a human sign-off on every change to the encryption path.

  </BreakPart>

<Drill id="a2-d1" scenario="You're designing a notes app. Your options: (a) standard encryption in transit and at rest, with password reset by email; (b) end-to-end, zero-knowledge encryption with no recovery if the password is forgotten. It's for a general audience of students." fields={[
  { label: "Your choice", options: ["(a) Standard, with email reset", "(b) Zero-knowledge, no recovery", "(b), plus a recovery key"] },
  { label: "Why, for these users?" }
]}>

**Expert answer: (a) for this audience, unless the notes are especially sensitive, in which case (b) with a recovery key.**

For a general student audience, forgotten passwords are common and losing all your notes forever is a disaster. Option (a) protects against the realistic threats (interception, stolen disks) while keeping recovery. Option (b) with no recovery is right for a password manager, whose whole value is that nobody else can read it, but wrong for most everyday apps.

This is the core lesson of A2: security choices are trade-offs against the product's users and qualities, not a contest to pick the strongest option. Write the decision, and its trade-offs, as an ADR.

</Drill>
